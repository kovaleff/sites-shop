# Предложения по функционалу (кроме оплаты)

Документ фиксирует, чего не хватает бирже сайтов для нормальной работы, помимо
платёжного контура. Предложения опираются на текущее состояние кода, а не на общие
пожелания: для каждого пункта указано, что именно в проекте отсутствует.

Оплата подписки и эквайринг намеренно не рассматриваются.

---

## Контекст: что уже есть

Чтобы не предлагать сделанное, кратко о текущем состоянии.

**Публичная часть.** Каталог (`CatalogView`) с фильтрами по тематике, зоне, цене
и доходу, пагинация по 25, диалог «Связаться» и «Пожаловаться», страницы
«Как это работает» и «Цены».

**Кабинет.** Список объявлений, создание/редактирование, смена статуса
(active / inactive / withdrawn / sold), скрытие проданных, сообщения и диалоги,
файл подтверждения домена, история платежей (данные), бейджи модерации.

**Админка (Orchid).** Пользователи, тематики, объявления, модерация, диалоги,
сообщения, платежи.

**Антиспам.** Модерация с автоапрувом по проверке домена, жалобы, капча,
Safe Browsing, возраст домена, лимиты (см. `.ai/antispam.md`).

**Чего нет совсем:** планировщика задач, почтовых уведомлений, публичного профиля
продавца, метатегов для поисковиков, сортировки и поиска в каталоге, счётчиков
просмотров, избранного, отзывов.

## P0 — без этого площадка не работает как бизнес

### 1. SEO и индексируемость

**Уточнение по JS-рендерингу.** Google действительно исполняет JavaScript
(Evergreen Googlebot, двухволновое индексирование: сначала HTML, потом рендер
в очереди). Поэтому «Google видит пустую оболочку» — неверно. Проблема в другом,
и она серьёзнее, чем рендеринг.

**Реальные проблемы (по коду).**

1. **Нет URL у лота.** В `resources/js/router/index.js` маршруты: `/`,
   `/how-it-works`, `/pricing`, `/cabinet/*`, `/:pathMatch(.*)*`. Отдельной страницы
   объявления не существует вообще — лот открывается только через диалог из каталога.
   Индексировать нечего, сколько бы хорошо Google ни рендерил JS.
2. **Соцсети JS не исполняют.** VK, Telegram, WhatsApp читают только серверный HTML.
   Сейчас в `app.blade.php` нет ни `og:title`, ни `og:image` — любая ссылка на биржу
   в VK/Telegram разворачивается пустой заглушкой. Для аудитории, которая логинится
   через VK ID, это прямая потеря трафика.
3. **Яндекс и Bing рендерят хуже и медленнее.** Яндекс JS-рендеринг поддерживает,
   но с ограничениями и задержками; Bing — частично. Для русскоязычной биржи Яндекс
   — значимая доля поиска.
4. **`<title>` ставится на клиенте** (`router.afterEach` в `router/index.js`).
   Google это поддерживает, но сам рекомендует отдавать заголовок в исходном HTML:
   при сбое рендера остаётся общий `<title>` из `app.blade.php`.
5. **Каталог — одна страница с query-параметрами.** Фильтры живут в `?price_min=…`,
   `?categories=…`. Фасетные URL Google не индексирует как отдельные страницы,
   а без `canonical` получаются дубли.
6. **`public/robots.txt` — `Disallow:` без списка**, то есть открыто всё, включая
   `/cabinet/`, `/admin/`, `/api/`. Служебные страницы попадут в индекс.
7. **Рендер отложен.** Пока Google дойдёт до рендера, лот может быть продан или снят.
   Для быстро меняющегося каталога это потерянные показы.

**Решение — «SSR-lite», без полного SSR.** Полноценный SSR на Vue+Vite потребует
отдельного сервера рендеринга и переделки точек входа — это дорого. Дешевле отдавать
серверный HTML только там, где он реально нужен:

- **Страница лота с сервера:** `GET /site/{id}-{slug}` (и/или `/site/{domain}`) —
  Blade-контроллер отдаёт `app.blade.php` с заполненными `<title>`,
  `<meta name="description">`, `og:title/og:description/og:image`, `canonical`
  и JSON-LD `Product`/`Offer`; данные лота кладутся в `window.__INITIAL_STATE__`,
  SPA подхватывает их и дальше работает как обычно. Поисковик и соцсети получают
  полноценный HTML, SPA — не переписывается.
- **Метатеги для статических страниц** (`/`, `/how-it-works`, `/pricing`) — в Blade,
  без JS.
- **`og:image`** — генерировать картинку лота (домен, цена, доход) или использовать
  сохранённый скриншот (см. п. 5).
- **`sitemap.xml`** — scheduled-команда `sitemap:generate` по `publiclyVisible()`
  лотам и тематикам, раз в сутки.
- **`robots.txt`** — `Sitemap:`, `Disallow: /cabinet/`, `/admin/`, `/api/`.
- **`canonical`** на каталоге — на «чистый» URL без фильтров, чтобы фасетные страницы
  не плодили дубли; страницы пагинации оставить индексируемыми, но с `canonical`
  на себя.

**Где менять.** `resources/views/app.blade.php` (секции под метатеги),
`routes/web.php` (маршрут лота до SPA-fallback), новый
`app/Http/Controllers/ListingPageController.php`, `resources/js/router/index.js`
(маршрут `/site/:id` + гидратация из `window.__INITIAL_STATE__`),
`routes/console.php`, `public/robots.txt`.

**Эффект:** высокий (поисковый трафик + превью в соцсетях). **Трудоёмкость:**
средняя при SSR-lite (1–2 дня), высокая при полном SSR. **Приоритет:** первый,
но именно в варианте SSR-lite.

### 2. Уведомления о сообщениях и решениях

**Проблема.** `app/Notifications` и `app/Mail` отсутствуют, `MAIL_MAILER=log`.
Продавец узнаёт о новом сообщении только если сам зашёл в кабинет. Покупатель,
написавший продавцу, может не дождаться ответа и уйти. Диалог — ядро сделки,
а без уведомлений он не работает.

**Решение.**
- `Notification`-классы: `NewMessageReceived`, `SiteModerated`, `SubscriptionExpiring`,
  `ReportResolved` (последние два — для продавца).
- Канал: email (`mail`), опционально Telegram-бот (у аудитории VK/Яндекс он популярен).
- Настройки уведомлений у пользователя: включить/выключить по типам, иначе письма
  начнут раздражать.
- Дайджест вместо спама: если сообщений много, отправлять не каждое, а раз в N минут
  (через `ShouldQueue` + задержку/`later`).
- Отписка по ссылке с токеном (`signed` URL) — требование к рассылкам.

**Где менять.** `app/Notifications/*`, `app/Http/Controllers/Api/MessageController.php`,
`ConversationController::store`, `Site::setModeration()` → событие,
`config/mail.php`, `.env` (`MAIL_MAILER=smtp`).

**Эффект:** очень высокий. **Трудоёмкость:** средняя (1–2 дня).

### 3. Планировщик задач и жизненный цикл подписки

**Проблема.** `routes/console.php` пуст, `withSchedule` не настроен — в проекте нет
ни одной периодической задачи. При этом `publiclyVisible()` требует
`paid_until >= today`: когда подписка истекает, объявление **молча** пропадает
из каталога. Продавец не получает предупреждения, не понимает, почему лот исчез,
и уходит.

**Решение.** Зарегистрировать расписание:
- `sites:notify-expiring` — ежедневно: за 7 и за 1 день до `paid_until` письмо
  «продлите подписку»; отдельное письмо в день истечения.
- `sites:unpublish-expired` — перевести истёкшие в `inactive` с записью причины,
  чтобы это было видно в кабинете, а не выглядело как баг.
- `sites:recheck-domains` — еженедельно перепроверять домены опубликованных лотов
  (из `.ai/antispam.md`, слой 3): домен умер или попал в Safe Browsing →
  `rejected` + уведомление.
- `sitemap:generate` — раз в сутки.
- `reports:digest` — утренняя сводка модератору о новых жалобах.

**Где менять.** `routes/console.php` (`Schedule::command(...)`),
`bootstrap/app.php` (`withSchedule` при необходимости), новые команды
в `app/Console/Commands/`. На сервере нужен cron:
`* * * * * php artisan schedule:run`.

**Эффект:** высокий. **Трудоёмкость:** низкая–средняя. **Приоритет:** сразу после SEO,
потому что это фундамент для всех напоминаний.

### 4. Публичная страница продавца

**Проблема.** Продавец виден только как имя в карточке лота и в диалоге. Нет
страницы «все лоты этого продавца», нет истории, нет возможности оценить надёжность
контрагента. Покупатель не понимает, с кем имеет дело.

**Решение.**
- `/seller/{id}` — публичный профиль: имя, аватар, дата регистрации, число
  опубликованных лотов, число проданных, бейдж «проверенный продавец»
  (есть подтверждённые домены), средний рейтинг (см. п. 11).
- Ссылка на профиль из карточки лота и из диалога.
- В кабинете — блок «Профиль продавца»: имя, аватар, описание, город/страна
  (опционально), ссылка на профиль.
- Сейчас редактирование профиля есть только в Orchid (`UserProfileScreen`),
  в SPA его нет — добавить `PATCH /api/v1/profile`.

**Где менять.** `app/Models/User.php`, новый `PublicProfileController`,
`resources/js/views/SellerView.vue`, `routes/web.php`, миграция с полями
`bio`, `city` (опционально).

**Эффект:** средний–высокий (доверие). **Трудоёмкость:** средняя.

### 5. Фавикон и скриншот лота

**Проблема.** `PublicSiteResource` отдаёт `faviconUrl => null` — жёстко зашито.
В `ListingCard` есть ветка рендера картинки, но она никогда не срабатывает: все
карточки показывают букву домена. Лоты выглядят одинаково, каталог — безлико.

**Решение.**
- Job `FetchSitePreview`: при подтверждении домена скачивать `favicon.ico` /
  `<link rel="icon">` и делать скриншот главной (через внешний сервис или
  headless-браузер), складывать в `storage/app/public/previews/{site_id}`.
- Хранить в `sites`: `favicon_path`, `preview_path`, `preview_updated_at`.
- Отдавать через `Storage::url()`, с плейсхолдером при отсутствии.
- Обновлять скриншот при смене домена и раз в месяц (в рамках п. 3).

**Где менять.** `PublicSiteResource`, `ListingCard.vue`, новый job, миграция,
`config/filesystems.php` (диск `public`).

**Эффект:** средний (конверсия каталога). **Трудоёмкость:** средняя.

## P1 — конверсия и качество каталога

### 6. Сортировка и текстовый поиск

**Проблема.** `CatalogController@index` жёстко сортирует по `created_at desc`.
Нет сортировки по цене/доходу (хотя индексы `sites_price_index`,
`sites_monthly_revenue_index` уже есть и не используются), нет поиска по названию
и домену.

**Решение.**
- Параметр `sort`: `newest` (по умолчанию), `price_asc`, `price_desc`,
  `income_desc`, `income_asc`. В UI — селект рядом с фильтрами.
- Параметр `q`: поиск по `title` и `domain` (`LIKE`), минимум 2 символа.
  Для больших объёмов — Scout + Meilisearch/Typesense (у проекта уже есть скил
  `scout-development`), но начинать можно с `LIKE` + индексы.
- Сохранять сортировку в query-строке (как сейчас делают фильтры через
  `useCatalogQuery`).

**Где менять.** `CatalogController`, `resources/js/lib/catalogFilters.js`,
`CatalogFilters.vue`, `stores/catalog.js`, `catalogService.js`.

**Эффект:** высокий. **Трудоёмкость:** низкая.

### 7. Избранное и подписка на фильтр

**Проблема.** Покупатель не может сохранить интересный лот или вернуться к нему.
Нет способа узнать о новых лотах по его критериям — он должен сам periodically
заходить и заново выставлять фильтры.

**Решение.**
- Таблица `favorites` (`user_id`, `site_id`, `created_at`, unique).
- Кнопка-сердечко на карточке лота и в кабинете раздел «Избранное».
- Уведомление, если лот из избранного продан или изменил цену.
- «Подписаться на фильтр»: сохранить набор фильтров (`saved_searches`), при
  появлении нового подходящего лота — письмо (раз в день/неделю, на выбор).

**Где менять.** Миграция, `Favorite`/`SavedSearch` модели, API-контроллеры,
`ListingCard.vue`, кабинет-навигация (`CabinetNav.vue`).

**Эффект:** средний–высокий (возврат пользователей). **Трудоёмкость:** средняя.

### 8. Метрики лота: просмотры

**Проблема.** Продавец не видит, работает ли объявление. В кабинете есть только
счётчик непрочитанных сообщений. Нельзя ответить на вопрос «повысить цену или
переписать описание».

**Решение.**
- Таблица `site_views` (`site_id`, `date`, `count`) или агрегат в `sites`:
  `views_count`, `views_today`.
- Инкремент при выдаче лота в каталоге (не на каждый рендер — батчем/кэшем,
  чтобы не писать в БД на каждый запрос) и на странице лота.
- В кабинете: «Просмотры: 128 · Сообщений: 3 · В избранном: 5» за 7/30 дней.
- Не считать ботов: фильтр по User-Agent + исключение известных краулеров.

**Где менять.** Миграция, `CatalogController` (кэш + `Cache::increment`),
`SiteCard.vue`, `SiteResource`.

**Эффект:** средний (удержание продавцов). **Трудоёмкость:** низкая–средняя.

### 9. Похожие лоты

**Проблема.** Зайдя в карточку, покупатель не видит альтернатив. Если лот не
подошёл — он уходит с сайта, а не смотрит соседние.

**Решение.** Блок «Похожие» в карточке лота: та же тематика, близкая цена
(±30%) и доход, исключая текущий. Запрос по `categories` + диапазон цены,
лимит 4–6. Позже — сортировка по косинусной близости описаний.

**Где менять.** `CatalogController` (метод `similar`), `PublicSiteResource`,
новый компонент `SimilarListings.vue`.

**Эффект:** средний. **Трудоёмкость:** низкая.

### 10. Сравнение лотов

**Проблема.** Покупатель выбирает между 3–5 лотами и держит цифры в голове.
Для рынка сайтов, где сравнивают цену, доход, окупаемость и тематику, это
неестественно.

**Решение.** Чекбокс «сравнить» на карточке, страница `/compare?ids=1,2,3`
с таблицей: цена, доход, окупаемость (месяцев), тематики, зона, проверен,
товарный знак. Хранить выбор в `localStorage`, без БД.

**Где менять.** `ListingCard.vue`, новая `CompareView.vue`, роутер,
`catalogService.js`.

**Эффект:** средний. **Трудоёмкость:** низкая.

## P2 — доверие и завершение сделки

### 11. Отзывы и рейтинг продавца

**Проблема.** Доверия нет вообще: единственный сигнал — бейдж «проверен»
(подтверждение домена). Покупатель не знает, отвечает ли продавец, честно ли
описывает доход, не бросает ли после предоплаты.

**Решение.**
- Таблица `reviews` (`site_id`, `author_id`, `rating` 1–5, `comment`,
  `published_at`), уникальность `(site_id, author_id)`.
- Оставить отзыв может только участник диалога по этому лоту (проверка по
  `conversations`), после того как лот получил `sold`.
- Агрегат в `users`: `rating_avg`, `reviews_count`; отображать в карточке лота
  и в профиле продавца.
- Модерация отзывов — через общую очередь (текст проходит тот же
  `NoAdvertisingContent`).
- Антинакрутка: один отзыв на пару «продавец-покупатель» по лоту, без отзывов
  от аккаунтов младше N дней.

**Где менять.** Миграция, `Review` модель, API, `SellerView.vue`, `ListingCard.vue`,
Orchid-экран.

**Эффект:** высокий (доверие = конверсия). **Трудоёмкость:** средняя–высокая.

### 12. Фиксация сделки

**Проблема.** Статус `sold` продавец ставит вручную, покупатель в этом не участвует.
Нет истории «кто купил, когда, за сколько». Нет повода для отзыва (п. 11) и нет
данных для статистики площадки.

**Решение.**
- Кнопка «Продан» в диалоге у продавца → запрос подтверждения покупателю →
  `sold` фиксируется с `sold_at`, `buyer_id`, `sold_price`.
- Покупатель может подтвердить или оспорить (модератор разбирает).
- Если покупатель молчит N дней — сделка считается состоявшейся по умолчанию.
- В кабинете — «История продаж» отдельным разделом (сейчас проданные просто
  скрываются в архив).

**Где менять.** Миграция (`buyer_id`, `sold_price`), `Site::changeStatus()`,
`ConversationController`, новый `SaleController`, кабинет.

**Эффект:** средний–высокий. **Трудоёмкость:** средняя.

### 13. Безопасность сделки в интерфейсе

**Проблема.** В переписке продавец легко уводит покупателя в Telegram и просит
предоплату. Площадка теряет сделку и репутацию, покупатель — деньги.

**Решение.**
- Дисклеймер в первом сообщении диалога и в карточке лота: «Не переводите деньги
  до передачи домена».
- Чек-лист безопасной сделки (отдельная страница, ссылка из диалога):
  проверка домена, передача через регистратора, эскроу-сервисы.
- Мягкая эвристика в сообщениях: при упоминании реквизитов/внешних мессенджеров —
  предупреждение отправителю (не блокировка, чтобы не ломать живые диалоги).
- Кнопка «Пожаловаться на продавца» прямо из диалога (сейчас жалоба только
  из каталога, `POST /api/v1/sites/{site}/reports`).

**Где менять.** `CabinetConversationView.vue`, `ConversationController`,
`SiteReportController` (расширить контекст), новая страница-чеклист.

**Эффект:** средний. **Трудоёмкость:** низкая.

## P3 — операционка и админка

### 14. Дашборд и воронка

**Проблема.** `PlatformScreen` — стандартная заглушка Orchid. Нет ответа на
вопросы «сколько лотов создаётся в неделю», «сколько доходит до публикации»,
«сколько сообщений на лот», «где теряются продавцы».

**Решение.** Виджеты на главном экране админки:
- создано / одобрено / отклонено / оплачено за период;
- конверсия: создание → подтверждение домена → публикация → первое сообщение → продажа;
- топ тематик и зон, средняя цена и доход;
- новые жалобы и объявления в очереди (со ссылками);
- просроченные подписки.

**Где менять.** `app/Orchid/Screens/PlatformScreen.php`, `Layout::metrics()`,
`TD`-таблицы, агрегирующие запросы (с индексами, см. п. 19).

**Эффект:** средний (управляемость). **Трудоёмкость:** средняя.

### 15. Единый экран жалоб и аудит модерации

**Проблема.** Жалобы видны только внутри карточки объявления. Модератор не может
посмотреть «все новые жалобы», а действия (approve/reject/приём жалобы) нигде
не логируются: непонятно, кто и почему снял лот.

**Решение.**
- Отдельный экран `admin/marketplace/reports`: фильтры по статусу и причине,
  сортировка по дате, переход к объявлению.
- Таблица `moderation_actions` (`site_id`, `user_id`, `action`, `reason`,
  `created_at`) — писать при каждом решении. Показывать историю в карточке.
- Это же — основа для разбора спорных ситуаций и для метрик качества модерации
  (доля отменённых решений).

**Где менять.** Новый `ReportListScreen`, миграция, `SiteEditScreen`,
`ModerationQueueScreen`.

**Эффект:** средний. **Трудоёмкость:** низкая–средняя.

### 16. Поиск и массовые операции в Orchid

**Проблема.** В списках объявлений/пользователей/жалоб фильтры есть, но нет
полнотекстового поиска по домену/названию/email. Найти конкретный лот по жалобе
неудобно. Массовых действий нет — каждое объявление обрабатывается по одному.

**Решение.** `->filters(...)` + `TD::FILTER_TEXT` для домена/названия/email,
командная кнопка «Одобрить выбранные» с подтверждением и записью в аудит (п. 15).

**Эффект:** низкий–средний. **Трудоёмкость:** низкая.

## Техническое здоровье

### 17. Троттлинг переписки

**Проблема.** `POST /api/v1/conversations` и `POST /api/v1/conversations/{id}/messages`
не имеют `throttle`. Авторизованный пользователь может залить диалог тысячей
сообщений, а также массово начинать диалоги по всем лотам — это и спам, и нагрузка.

**Решение.** `throttle:30,1` на отправку сообщений, `throttle:10,1` на старт
диалога, лимит активных диалогов на пользователя в сутки.

**Где менять.** `routes/web.php`, `AppServiceProvider` (`RateLimiter::for`).

**Эффект:** средний. **Трудоёмкость:** очень низкая.

### 18. Мониторинг, бэкапы, health

**Проблема.** Нет ни одной точки наблюдаемости: ошибки только в `storage/logs`,
очередь может встать незамеченной (а от неё зависит публикация объявлений),
бэкапов БД нет.

**Решение.**
- `/up` уже есть (health), дополнить проверкой БД и очереди.
- Laravel Pulse для метрик запросов/очереди (или Nightwatch, если предпочтительнее).
- Внешний uptime-монитор на `/up`.
- Ежедневный `mysqldump` + `storage/app` в S3/внешнее хранилище, проверка
  восстановления раз в квартал.
- Алерт, если `failed_jobs` растёт или `VerifySiteDomain` падает подряд.

**Эффект:** высокий (предотвращает тихие поломки). **Трудоёмкость:** низкая.

### 19. Кэш каталога и индексы под новые запросы

**Проблема.** Каталог считает `count(*)` по фильтрам на каждый запрос, а после
появления сортировки/поиска (п. 6) и дашборда (п. 14) запросы станут тяжелее.
Существующие индексы (`sites_price_index`, `sites_monthly_revenue_index`,
`sites_visibility_index`) не покрывают комбинации «статус + модерация + сортировка».

**Решение.**
- Составной индекс `(status, moderation_status, created_at)` и
  `(status, moderation_status, price)`.
- Кэшировать первую страницу каталога и счётчики зон на 60 секунд,
  сбрасывать при создании/изменении объявления.
- Проверить `EXPLAIN` на реальных данных перед релизом.

**Эффект:** средний (скорость). **Трудоёмкость:** низкая.

## Быстрые победы (до одного дня каждая)

1. `throttle` на сообщения (п. 17) — 30 минут.
2. Сортировка каталога (п. 6, только `sort`) — пара часов.
3. Ссылка `Sitemap:` в `robots.txt` + `noindex` для `/cabinet` — час.

## Что не делать сейчас

- **Полный SSR (Nuxt / отдельный Node-сервер рендеринга).** Google исполняет JS,
  поэтому полный SSR не окупается. Достаточно SSR-lite: серверные метатеги
  на странице лота (п. 1).
- **Чат в реальном времени (WebSocket).** Текущий HTTP-опрос/ручное обновление
  достаточны для десятков диалогов. Reverb добавит инфраструктуру без выгоды.
- **Мобильное приложение.** PWA-режим дешевле и покрывает потребность.
- **Мультиязычность.** Аудитория русскоязычная; i18n удвоит тексты в формах
  и валидации без выгоды.
- **Публичный API для партнёров.** Нет спроса, а поддержка контракта стоит денег.
- **Эскроу собственной разработки.** Юридически сложно; лучше интеграция
  с существующим сервисом, когда сделки станут регулярными.
