# Phase 0 Research: Модели данных биржи по продаже сайтов

**Feature**: `001-marketplace-data-model` | **Date**: 2026-10-28

Все пункты Technical Context определены; `NEEDS CLARIFICATION` не осталось. Ниже — решения, которые влияют на схему и поведение моделей.

## 1. Именование сущности объявления

**Decision**: модель `App\Models\Site`, таблица `sites`.

**Rationale**: В спецификации сущность называется «Продаваемый сайт (Site / Listing)», а предмет проекта — биржа сайтов. `Site` короче в связях (`$site->categories`, `$conversation->site`) и не конфликтует с другими классами приложения. Таблица `sites` совпадает с именем проекта (`sites-shop`).

**Alternatives considered**:
- `Listing` / `listings` — точнее передаёт «объявление», но длиннее и не совпадает с ключевой сущностью спецификации.
- `Website` / `websites` — вводит третий синоним, которого нет в спецификации.

## 2. Подписка на уровне объявления

**Decision**: `sites.paid_until` типа `date`, nullable. Отдельной таблицы подписок нет; история — в `subscription_payments`.

**Rationale**: FR-010 и FR-027 требуют независимой даты у каждого объявления. Дата — единственный источник истины для видимости; история платежей хранит основания. `date` достаточно, потому что видимость сравнивается с текущей датой (FR-012).

**Alternatives considered**:
- `paid_until` на `users` — нарушает независимость объявлений.
- Таблица `subscriptions` с периодами — дублирует `paid_until`, усложняет запрос каталога и не даёт выгоды в v1.
- `datetime` — избыточная точность; оплата измеряется днями.

## 3. Публичная видимость

**Decision**: локальный scope `publiclyVisible()` и метод `isPubliclyVisible()`; глобального scope нет. Условие: `status = active AND paid_until IS NOT NULL AND paid_until >= today`.

**Rationale**: Владелец должен видеть свои непубличные объявления (FR-013, FR-022), а служебные задачи — работать со всеми записями. Глобальный scope молча искажал бы выборки. Условие совпадает с FR-012 и SC-004.

**Alternatives considered**:
- Глобальный scope — скрывает данные от владельца и ломает администрирование.
- Материализованный флаг `is_visible` — требует ежедневного пересчёта и рассинхронизируется; дата и так индексируется.
- Отдельная таблица видимости — избыточна.

## 4. Уникальность домена с возможностью повторной публикации

**Decision**: домен хранится нормализованным (нижний регистр, без `www.`, без завершающего `/`). Добавляется генерируемый stored-столбец `public_domain`:

```sql
case when status in ('active', 'inactive') then domain else null end
```

На `public_domain` — уникальный индекс. NULL не участвуют в уникальности, поэтому снятые и проданные объявления домен не занимают.

**Rationale**: FR-009 запрещает дубликат только среди «Активен»/«Неактивен», а Edge Cases разрешают повторно выставить домен после «Снят с продажи»/«Продан». Обычный уникальный индекс по `domain` это сломал бы. Генерируемый столбец обеспечивает ограничение на уровне БД без гонок. Синтаксис `storedAs()` поддержан грамматиками MySQL и SQLite; проверено на SQLite 3.37.2 и в `SQLiteGrammar`/`MySqlGrammar` Laravel 13.39.0.

**Alternatives considered**:
- Проверка только в приложении — гонка при параллельных запросах.
- Обычный `unique(domain)` — блокирует законную повторную продажу.
- Partial index (`WHERE status IN (...)`) — MySQL не поддерживает; Laravel не предоставляет API.
- Отдельная таблица занятых доменов — лишняя синхронизация.

**Caveat**: значения статусов в выражении фиксируются в миграции; при добавлении нового «публичного» статуса потребуется новая миграция. Это осознанный компромисс.

## 5. Представление статуса объявления

**Decision**: `varchar(16)` + PHP-enum `App\Enums\ListingStatus` (`Active = 'active'`, `Inactive = 'inactive'`, `Withdrawn = 'withdrawn'`, `Sold = 'sold'`) с cast в модели. Переходы описываются методами enum.

**Rationale**: Нативный MySQL `ENUM` усложняет изменение набора значений и плохо переносится на SQLite. PHP-enum даёт типизацию, читаемые переходы и единый источник значений для валидации. Ограничение «ровно одно значение» обеспечивается cast + доменным методом `changeStatus()`.

**Alternatives considered**:
- Нативный `ENUM` — жёстко привязан к MySQL, миграции болезненны.
- Отдельная таблица статусов — избыточна для четырёх фиксированных значений.
- Пакет state machine — новая зависимость без выгоды для четырёх состояний.

## 6. Диалоги и сообщения

**Decision**: `conversations` (`site_id`, `buyer_id`, `seller_id`, `last_message_at`) с уникальностью `(site_id, buyer_id)`; `messages` (`conversation_id`, `sender_id`, `body`, `read_at`). `seller_id` денормализован из владельца объявления на момент создания диалога.

**Rationale**: FR-029 требует один диалог на пару «объявление + покупатель»; FR-030 — проверку участия. `seller_id` делает проверку доступа дешёвой и не зависит от будущей смены владельца (в v1 не поддерживается, но история сохраняется). `read_at` на сообщении достаточен, потому что у каждого сообщения ровно один получатель — второй участник. `last_message_at` ускоряет сортировку списка диалогов (FR-023).

**Alternatives considered**:
- Сообщения без диалога (одна таблица `messages`) — не выполняет FR-029/FR-030.
- Один диалог на продавца — смешивает объявления.
- Отдельная таблица участников — избыточна для двух фиксированных ролей.
- `read_at` на паре «сообщение + пользователь» — нужно только для групповых чатов, которых нет.

## 7. Продление подписки и платежи

**Decision**: `subscription_payments` хранит `site_id`, `user_id` (плательщик), `amount`, `currency` (по умолчанию `RUB`), `period_months`, `status`, `paid_at`, `external_id`. `SubscriptionPayment::markAsPaid()` в транзакции блокирует платёж и объявление, проверяет допустимость оплаты и вызывает `Site::extendSubscription()`. Новая дата: `max(paid_until, today)->addMonthsNoOverflow(period_months)`.

**Rationale**: FR-011 и FR-028 требуют продлевать только указанное объявление и отклонять оплату для «Снят с продажи»/«Продан». `lockForUpdate` и проверка текущего статуса делают операцию идемпотентной при повторном вызове и защищают от двойного продления. `addMonthsNoOverflow` корректно обрабатывает конец месяца (31 января + 1 месяц = 28/29 февраля).

**Alternatives considered**:
- Вычислять дату «на лету» из платежей — усложняет каталог и не даёт быстрого фильтра.
- Продлевать от `now()` всегда — теряет уже оплаченные дни (FR-011 требует от более поздней даты).
- Отдельный сервис/action-класс — новый каталог `app/Actions`; в v1 достаточно метода модели.
- Хранить провайдерские токены — не требуется спецификацией и повышает риск утечки.

## 8. Поля социальной аутентификации

**Decision**: в `users` добавить `avatar` (nullable), `vk_id` (nullable, unique), `ya_id` (nullable, unique), `vk_last_login_at`, `ya_last_login_at`. `email` и `password` сделать nullable, `email` остаётся unique.

**Rationale**: FR-001/FR-002 требуют находить аккаунт по идентификатору провайдера и не требовать пароль. Уникальные индексы обеспечивают «одна внешняя учётная запись — один аккаунт». Отдельный `provider` не нужен: провайдер выводится из заполненного идентификатора, а объединение аккаунтов запрещено (Assumptions). Токены доступа не сохраняются — они не нужны для входа и являются секретом.

**Alternatives considered**:
- Таблица `social_identities` — гибче для многих провайдеров, но избыточна для двух и усложняет выборку.
- Обязательный пароль — противоречит входу без пароля.
- `vk_photo`/`ya_photo` отдельно (как в `cheap-eats`) — дублирование; один `avatar` на аккаунт достаточно, так как аккаунты не объединяются.
- `vk_access_token` (как в `cheap-eats`) — отклонено по соображениям безопасности.

## 9. Тематики

**Decision**: `categories` (`name` unique, `slug` unique) + pivot `category_site`. Сидер наполняет 31 уникальную тематику; `slug` генерируется из названия через `Str::slug()` при создании.

**Rationale**: FR-005/FR-006 требуют many-to-many и уникальных названий; `slug` — стабильный публичный идентификатор для ссылок. `Str::slug()` транслитерирует кириллицу; проверено: 31 название даёт 31 уникальный slug. Точный дубликат «Медицина и здоровье» объединён с «Здоровье и медицина».

**Alternatives considered**:
- JSON-массив в `sites` — не даёт ссылочной целостности и фильтрации по индексу.
- Одна тематика на объявление — противоречит требованию.
- Ручные slug в сидере — риск рассинхронизации; генерация в модели надёжнее.

## 10. Деньги

**Decision**: `price` и `monthly_revenue` — `decimal(12,2)`, `amount` платежа — `decimal(10,2)`, cast `decimal:2`.

**Rationale**: RUB с копейками; decimal не накапливает ошибки округления и корректно сравнивается в диапазонных фильтрах. Точность 2 знака соответствует денежным значениям.

**Alternatives considered**:
- Целые копейки — точнее, но требует преобразований во всех слоях и усложняет читаемость.
- `float` — ошибки округления и нестабильные сравнения.

## 11. Фабрики и сидеры

**Decision**: фабрики для всех новых моделей; состояния `active`, `inactive`, `withdrawn`, `sold`, `unpaid`, `paid`, `expired`, `withTrademark`; `UserFactory` получает состояния `vk()` и `yandex()`. `CategorySeeder` идемпотентен (`firstOrCreate`) и вызывается из `DatabaseSeeder`.

**Rationale**: Тесты должны описывать сценарии декларативно, без ручной сборки атрибутов. Идемпотентный сидер безопасен при повторном запуске. Существующий `DatabaseSeeder` уже создаёт демо-пользователя — поведение сохраняется.

**Alternatives considered**:
- Сиды прямо в тестах — дублирование.
- `truncate` перед сидом — ломает внешние ключи и повторный запуск.

## 12. Тестовая среда и проверка схемы

**Decision**: тесты — PHPUnit feature-тесты на SQLite in-memory; миграции дополнительно прогоняются на MySQL в рамках быстрой проверки.

**Rationale**: `phpunit.xml` уже настроен на SQLite; это быстро и изолированно. Генерируемый столбец и уникальный индекс проверены на SQLite 3.37.2; MySQL 8.0.46 поддерживает тот же синтаксис. Прогон на MySQL ловит различия грамматик до релиза.

**Alternatives considered**:
- Тесты только на MySQL — медленнее и требует внешней БД в CI.
- Отказ от генерируемого столбца ради одинаковости — теряет защиту FR-009.

## 13. Подтверждение принадлежности сайта

**Decision**: в `sites` добавить `verification_filename` (`varchar(64)`, unique, not null) и `verified` (`boolean`, default `false`). Имя файла генерируется в `Site::booted()` на событии `creating` как `Str::lower(Str::random(32)).'.txt'`, если не задано; поле не входит в `#[Fillable]` и не меняется при обновлении. `verified` также вне `#[Fillable]`; для администратора предусмотрен доменный метод `markVerified(bool $verified = true): void`.

**Rationale**: FR-031/FR-032 требуют уникальное случайное имя файла, создаваемое один раз, и флаг, который меняет только администратор. 32 символа из `Str::random()` дают непредсказуемое имя, а уникальный индекс исключает коллизию. Генерация в событии `creating` гарантирует значение для записей, созданных через фабрику, сидер или консоль, и не зависит от контроллера. Исключение полей из `#[Fillable]` закрывает mass assignment со стороны продавца. `verified` не участвует в `publiclyVisible()` — это дополнительный признак доверия, а не условие каталога.

**Alternatives considered**:
- UUID как имя файла — длиннее и содержит дефисы; случайная строка проще для ручного размещения.
- Отдельная таблица `site_verifications` — избыточна: проверка одна на объявление, история в v1 не требуется.
- Разрешить продавцу задавать имя файла — позволяет подставить чужой файл и создаёт коллизии.
- Автоматическая проверка файла по HTTP — внешняя интеграция, вне фазы моделей.
- Учитывать `verified` в видимости — противоречит FR-032 и усложняет каталог без требования.

## 14. Отложенные решения

Следующие пункты сознательно не входят в фазу моделей и не блокируют её:

- Form Requests и правила валидации FR-020/FR-025 (формат домена, минимальные длины, «хотя бы одна тематика», лимит 2000 символов).
- Административный интерфейс проверки владения и автоматическая загрузка/проверка файла по HTTP; в фазе моделей есть только поля и `markVerified()`.
- Политики и контроллеры, OAuth-редиректы, платёжный провайдер, UI.
- Уведомления, модерация, изображения, удаление аккаунтов.

Они перечислены в `plan.md` → Scope Coverage и должны быть запланированы отдельной фазой HTTP-слоя.

## No New Dependencies

Все решения реализуются средствами Laravel 13.39.0 и PHP 8.3. Новые пакеты не требуются.
