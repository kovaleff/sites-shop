# Research: Все модели в административной панели

**Feature**: `002-orchid-admin-models` | **Date**: 2026-10-28 | **Plan**: [plan.md](./plan.md)

Технический контекст не содержит маркеров `NEEDS CLARIFICATION`: все неизвестные закрыты существующей кодовой базой, спецификацией и API Orchid 14.53.

## R1. Способ реализации разделов

**Decision**: Использовать отдельные классы `Screen` с layout-классами `Table` и `Rows` для каждой сущности, по образцу сгенерированных `UserListScreen`, `UserEditScreen`, `RoleListScreen` и `RoleEditScreen`.

**Rationale**: Проект уже использует этот паттерн; он даёт полный контроль над фильтрами, правами, guardrails и read-only-режимом. Orchid 14.53 поддерживает маршрут `Route::screen()`, который регистрирует `GET|HEAD|POST` с необязательным сегментом `{method?}`.

**Alternatives considered**:
- Универсальный CRUD-генератор или сторонний пакет — отклонён: не позволяет точечно соблюсти правила статусов, подтверждения владения и запрета редактирования служебных полей.
- Один экран с вкладками для всех сущностей — отклонён: ухудшает навигацию и не соответствует требованию отдельных ссылок в меню.

## R2. Права доступа и видимость меню

**Decision**: Зарегистрировать пять прав `platform.marketplace.categories`, `platform.marketplace.sites`, `platform.marketplace.conversations`, `platform.marketplace.messages`, `platform.marketplace.payments`. Пользователи продолжают использовать существующее право `platform.systems.users`. Каждый экран объявляет своё право через `permission()`, каждый пункт меню — через `->permission()`.

**Rationale**: Orchid проверяет `hasAnyAccess()` на уровне экрана и скрывает пункты меню без права. Это напрямую закрывает FR-003 и FR-029. Пять прав дают гибкое разграничение без изменения модели ролей.

**Alternatives considered**:
- Одно общее право `platform.marketplace` — отклонено: не позволяет выдать доступ только к платежам или только к тематикам.
- Проверка ролей вручную в экранах — отклонено: дублирует встроенный механизм Orchid и хуже тестируется.

## R3. Guardrails при редактировании объявления

**Decision**: В `SiteEditScreen` коммерческие поля сохраняются через `fill()`/`save()`, подтверждение владения — только через `Site::markVerified()`, смена статуса — только через `Site::changeStatus()`. Поля `verification_filename`, `paid_until`, `sold_at`, `user_id` отображаются только для чтения и не входят в форму сохранения. Сохранение выполняется в транзакции с перехватом `DomainException`.

**Rationale**: Модель `Site` уже содержит эти инварианты (FR-019, FR-020, FR-021). Прямое присвоение `status` или `verified` обошло бы правила переходов и административную монополию на подтверждение.

**Alternatives considered**:
- Разрешить редактирование всех полей через `forceFill()` — отклонено: нарушает инварианты и FR-019.
- Отдельные кнопки для каждого поля — отклонено: избыточно для первой версии.

## R4. Фильтры списков

**Decision**: Для фильтров по колонкам использовать `$allowedFilters` модели и `TD::filter()` с типами `FILTER_TEXT`, `FILTER_SELECT`, `FILTER_NUMBER_RANGE`, `FILTER_DATE_RANGE`. Для фильтров по связям (тематика объявления, участник диалога, отправитель сообщения, плательщик) — `Selection`-layout с отдельными классами `Filter`.

**Rationale**: Orchid 14.53 из коробки поддерживает `Where`, `Like`, `WhereMaxMin`, `WhereDateStartEnd`, а `NumberRange` формирует `filter[column][min]`/`[max]`. Это минимизирует код и использует штатное поведение. Связи требуют `whereHas`, поэтому для них нужны собственные фильтры.

**Alternatives considered**:
- Все фильтры через `Selection` — отклонено: больше классов и дублирование уже поддерживаемых типов.
- Фильтрация в контроллере вручную — отклонено: теряется штатное сохранение фильтров в URL и сброс пагинации.

## R5. Только чтение для диалогов, сообщений и платежей

**Decision**: Экраны `ConversationShowScreen`, `MessageShowScreen`, `SubscriptionPaymentShowScreen` не объявляют публичных методов-действий, кроме `query`, и не содержат `commandBar` с сохранением/удалением. Списки также не имеют действий удаления.

**Rationale**: Orchid ограничивает `{method?}` списком публичных методов экрана, поэтому POST на несуществующее действие не попадает в экран и отклоняется с `405` (URI перехватывает fallback-маршрут панели `admin/{fallbackPlaceholder}`, доступный только для GET). Это делает read-only-гарантию проверяемой на HTTP-уровне (FR-024, FR-026).

**Alternatives considered**:
- Скрывать кнопки через `canSee()` — отклонено: не защищает от прямого POST.
- Отдельное право «только чтение» — отклонено: избыточно, разделы и так не предполагают записи.

## R6. Политика удаления

**Decision**: Не добавлять удаление объявлений и пользователей. Для тематик удаление разрешено только при отсутствии связанных объявлений. Платежи, диалоги и сообщения не удаляются.

**Rationale**: Каскадное удаление объявления уничтожило бы историю переписки и платежей, а удаление пользователя — его объявления и диалоги. Спецификация (FR-028) прямо исключает destructive-удаление в первой версии.

**Alternatives considered**:
- Soft deletes — отклонены: требуют миграций и меняют поведение существующих моделей.
- Каскадное удаление — отклонено: необратимая потеря бизнес-данных.

## R7. Связанные данные в карточке пользователя

**Decision**: Дополнить существующий `UserEditScreen` тремя таблицами только для чтения: последние 10 объявлений, последние 10 диалогов (как покупатель или продавец) и последние 10 платежей. Данные загружаются в `query()` отдельными запросами с `with()`/`withCount()`.

**Rationale**: FR-007 требует показать связанные сущности, а отдельные экраны для этой связи создали бы дублирование. Ограничение в 10 записей сохраняет скорость карточки.

**Alternatives considered**:
- Отдельный экран «Активность пользователя» — отклонён: лишний маршрут и пункт меню.
- Полные списки с пагинацией внутри карточки — отклонены: несколько пагинаторов на одной странице конфликтуют.

## R8. Тестирование

**Decision**: PHPUnit feature-тесты через `actingAs($admin)->get(route(...))` и `post(route(..., ['method' => 'save']), $payload)`. Для проверки прав создавать пользователей с явным массивом `permissions`. Использовать существующие фабрики и `RefreshDatabase`.

**Rationale**: Это проверяет реальные HTTP-границы, включая `permission()`, ограничения методов маршрута и guardrails. Orchid dispatch-ит действия по имени последнего сегмента маршрута, поэтому тесты воспроизводят поведение браузера.

**Alternatives considered**:
- Тестировать только модели — отклонено: не покрывает права, меню и read-only-гарантии.
- Orchid Screen Testing helpers — отклонены: не проверяют HTTP-коды и ограничения маршрутов.

## R9. Права существующего администратора

**Decision**: Новые администраторы получают все права автоматически через `Dashboard::getAllowAllPermission()`. Для уже созданного `admin@example.com` в `quickstart.md` описано разовое обновление массива прав всеми зарегистрированными правами.

**Rationale**: Массив прав хранится в записи пользователя и не обновляется автоматически при добавлении новых прав. Без разового шага существующий администратор не увидит новые пункты меню.

**Alternatives considered**:
- Выдать wildcard `platform.*` — отклонено: слишком широко и не соответствует точечной модели прав.
- Автоматически выдавать права при каждом запросе — отклонено: неявное изменение прав пользователей.

## R10. Язык интерфейса

**Decision**: Новые экраны, меню и сообщения — на русском языке. Существующие экраны пользователей, ролей и примеров не переводятся.

**Rationale**: Спецификация и бизнес-требования на русском; администраторы биржи русскоязычные. Перевод существующих экранов выходит за рамки задачи.

**Alternatives considered**:
- Английский, как в сгенерированных экранах, — отклонён: снижает понятность для целевых администраторов.
- Полная локализация панели — отклонена: расширяет объём задачи.

## R11. Производительность списков

**Decision**: Использовать `with()` для владельца, тематик, участников и связанных объявлений, `withCount()` для счётчиков, `defaultSort()` и пагинацию Orchid. Не загружать сообщения в списках диалогов.

**Rationale**: Предотвращает N+1 и укладывается в цель «менее 2 секунд при 10 000 объявлений» (SC-011).

**Alternatives considered**:
- Ленивая загрузка связей — отклонена: N+1 на каждой строке.
- Кэширование списков — отклонено: преждевременно для административного интерфейса.

## R12. Отсутствие изменений схемы данных

**Decision**: Новых миграций и моделей нет. Единственное изменение модели — добавление `$allowedFilters` в `Site` для штатных фильтров Orchid.

**Rationale**: Все сущности уже существуют в `001-marketplace-data-model`. Административный слой — представление и управление, а не новая схема.

**Alternatives considered**:
- Денормализованные поля для поиска — отклонены: избыточны при текущих объёмах.
